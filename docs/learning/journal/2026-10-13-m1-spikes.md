# 2026-10-13 — M1: seven spikes on how to pass a message into a session

## What I built
Almost no product code. M1 was about **proving things before building on them**. I ran seven small experiments (spikes) against real Claude Code 2.1.296 sessions on Windows 11, to find out how a script can hand a waiting session its next message. Each one is written up in `docs/spikes/` with real output. To run them, I built a small test harness that drives an interactive Claude Code session the way a person would. I also fixed one real bug in `.gitignore` along the way.

## Why it's built this way
Relay's whole job is one move: when the lead finishes a reply tagged `TO CODE:`, that text must arrive in the builder as its next instruction, and the builder's report must come back the same way. The Claude Code docs describe several features that *might* do this, but they don't answer the questions that matter to Relay. What does the screen show while a hook waits? What happens at a timeout, or when Dennis presses Esc? Is there a hidden limit? Building M2–M4 on guesses could mean rebuilding them later, so `CLAUDE.md` says: test it first.

**Why real interactive sessions and not `claude -p`?** Relay runs inside sessions Dennis has open in a terminal. Headless mode (`claude -p`) behaves differently: there's no screen, no Esc, no idle prompt. So the spikes had to use the real interactive program, which expects a person at a keyboard. That's what the pty harness is for (see below).

**Why the spike code isn't in Git:** it's throwaway. Only the findings matter, and they're in `docs/spikes/`. The code lives in `spikes/` at the repo root, which `.gitignore` excludes. Short excerpts are quoted below so this entry makes sense on its own.

### The answers, in one table

| # | Question | Answer |
|---|---|---|
| 001 | Can a Stop hook hand Claude a new instruction? | Yes. Claude acts on `additionalContext` as a full instruction. |
| 002 | Is there a limit? | Yes: 8 continuations in a row, then the turn ends silently. A tool call in between resets the count; `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises it. |
| 003 | Can a hook wait 15 minutes? | Yes, with `timeout: 3600`. The screen says `running Stop hook`. Esc kills the hook at once. |
| 004 | What happens at the timeout? | The hook is killed silently and the baton is dropped. Leaving early and **re-arming** avoids it. |
| 005 | Can a background hook wake an *idle* session? | Yes, with `asyncRewake`, and no continuation cap. But old waiters pile up and can hijack a turn. |
| 006 | Could Claude Code's built-in messaging do the job? | It works, but Claude chooses whether and what to send, so a missed message fails silently. A complement only. |
| 007 | Does it all still work from the phone? | Yes. A phone prompt is just a normal turn on the PC. |

These answers feed ADR 0002 (the delivery mechanism), which is waiting for Dennis's OK.

## Code walkthrough

### The pty harness: `spikes/_pty/pty.cjs`
Interactive Claude Code draws a screen and waits for keys, so a normal script can't drive it. The harness fakes a terminal:
```js
const pty = require('@lydell/node-pty');
const { Terminal } = require('@xterm/headless');
const term = new Terminal({ cols, rows, allowProposedApi: true });
const env = Object.fromEntries(
  Object.entries(process.env).filter(([k]) => !/^CLAUDE/i.test(k)),
);
const p = pty.spawn(exe, args, { name: 'xterm-256color', cols, rows, cwd: workdir, env });
p.onData((d) => term.write(d));
```
- `pty.spawn` starts `claude.exe` inside a **pseudo-terminal**. Claude Code thinks a person is watching.
- Everything Claude Code prints goes into `@xterm/headless`, a terminal with no window. It works out what the screen *would* look like, so the harness can save it as plain text (`screen.txt`) once a second.
- The `env` filter was a lesson. My own session sets variables like `CLAUDE_CODE_CHILD_SESSION`, and a child that inherited them **stopped saving its transcript**. Dropping every `CLAUDE*` variable makes the child behave like a session Dennis opened himself.
- Keys come from a file: each line appended to `cmd.txt` (`send:hello`, `enter`, `esc`, `quit`) is turned into the matching bytes, such as `'\r'` for Enter and `'\x1b'` for Esc.

`spikes/_pty/launch.sh` starts the harness in the background and answers the "Do you trust this folder?" prompt by sending `down` and `enter`. The test sessions run in `C:\Users\denni\relay-sandbox\`, outside the repo, so Relay's own `CLAUDE.md` doesn't load into them and change their behaviour.

### A Stop hook that waits and then delivers: `spikes/004/rearm.cjs`
```js
process.stdin.on('end', () => {
  const j = JSON.parse(input);                       // hook input arrives as JSON on stdin
  const tick = setInterval(() => {
    if (fs.existsSync(msgFile)) {                    // the "message" has arrived
      clearInterval(tick);
      out(fs.readFileSync(msgFile, 'utf8'));
    } else if (Date.now() - t0 > SELF_DEADLINE * 1000) {
      clearInterval(tick);
      out('Relay: no message yet. Reply with only: WAITING');   // re-arm
    }
  }, 500);
});
function out(msg) {
  process.stdout.write(JSON.stringify({ hookSpecificOutput: { hookEventName: 'Stop', additionalContext: msg } }));
}
```
- Claude Code runs the hook when Claude finishes a reply and writes the hook's input to its stdin. The hook reads it all, then parses it.
- Every half second it checks whether a message file exists. In Relay, the Relay Helper would write that file.
- Writing `additionalContext` to stdout tells Claude Code "don't stop; here's more to do". Claude then acts on the text (spike 001).
- **Re-arm:** if no message has come before its own deadline, the hook asks for a tiny `WAITING` reply instead of letting Claude Code kill it at the timeout. That reply ends the turn, which fires a fresh Stop hook, which waits again (spike 004).

### A background hook that wakes an idle session: `spikes/007/rewake.cjs`
```js
if (fs.existsSync(msgFile)) {
  const msg = fs.readFileSync(msgFile, 'utf8');
  fs.unlinkSync(msgFile);
  process.stderr.write(msg);   // asyncRewake shows stderr to Claude
  process.exitCode = 2;        // exit code 2 = "wake the session"
}
```
Registered with `"asyncRewake": true`, so the session doesn't wait for it. Claude finishes, the prompt comes back, and the session is **idle**. When the hook later exits with code 2, Claude Code wakes the session and Claude acts on the message (spike 005). It uses `process.exitCode = 2` rather than `process.exit(2)` so Node finishes writing stderr before the process ends.

### The bug: `.gitignore` and `test/gitignore.test.ts`
The rule `spikes/` matched *any* folder named `spikes`, including `docs/spikes/`, so the write-ups were silently ignored. The fix is `/spikes/` (only the folder at the repo root). `test/gitignore.test.ts` (lines 7–19) asks Git itself with `git check-ignore -q --no-index <path>`, which exits with 0 if a path is ignored. The full story is in `docs/learning/bugs/001-gitignore-hid-spike-docs.md`.

## New concepts

### Pseudo-terminal (pty)
A fake terminal made by software. The program inside it behaves exactly as if a person were at a real terminal, while your script reads what it prints and sends it keystrokes. Example: `pty.spawn('claude.exe', [], { cols: 140, rows: 45 })`, then `p.write('\r')` presses Enter.

### Exit codes as signals
A program's exit code is a number it hands back when it ends. Claude Code gives some codes special meanings for hooks: `0` means "fine, carry on", and `2` means "blocking" (for an `asyncRewake` hook, "wake the session and show my stderr"). Example: `process.exitCode = 2` at the end of a Node script.

### Polling
Checking for something again and again on a timer, instead of being told when it happens. The spike hooks poll for `msg.txt` every 500 ms with `setInterval`. It's simple and reliable. The cost is a short delay and a little CPU.

### Timeouts and silent failure
Claude Code kills a hook that runs past its `timeout`. Spike 004 showed that nothing appears on screen when this happens, and the hook gets no chance to clean up. When a failure is silent, your own code must notice it, for example by recording the waiter's PID and deadline and checking them later. That's why the Relay Helper will need **dead-waiter detection**.

### Continuation cap
A safety limit in Claude Code: a Stop hook can make Claude keep going at most 8 times in a row in one turn. It stops runaway loops, but it would also stop a long Relay run. It can be raised with the environment variable `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`.

## Tests
The spikes are experiments, not tests. Their evidence is the logs and screens pasted into each write-up. The one product change, the `.gitignore` fix, is guarded by `test/gitignore.test.ts`. ## Self-check
1. Why couldn't the spikes use `claude -p` to test Relay's behaviour?
2. What happens to the baton when a waiting Stop hook reaches its timeout, and how does re-arming avoid it?
3. Why did the harness remove `CLAUDE*` environment variables before starting a child session?
4. Name one strength and one weakness of an `asyncRewake` Stop hook compared with a blocking one.
5. Why is cross-session messaging only a complement, even though it worked in every round?

<details><summary>Answers</summary>

1. Relay runs inside interactive sessions Dennis has open. Headless mode has no screen, no Esc and no idle prompt, so it can't show how those behave.
2. The hook is killed silently and the session goes idle with nobody waiting for the next message: the baton is dropped. Re-arming means the hook leaves before its deadline and asks for a tiny `WAITING` reply. That reply ends the turn and starts a fresh hook, so a waiter always exists.
3. A child session inherited variables such as `CLAUDE_CODE_CHILD_SESSION` from the session running the harness, which made it stop saving its transcript. Removing them makes the child behave like a normal session.
4. Strength: the session is idle while waiting, so Dennis can type freely, and there's no continuation cap. Weakness: old waiters aren't stopped when a new turn starts, so they pile up and one can fire mid-turn and hijack Dennis's own task. Relay must allow only one waiter per session.
5. Claude decides whether to call `SendMessage` and rewrites the content in its own words. If it forgets once, nothing notices and the relay stops. Hooks run as code every time.

</details>
