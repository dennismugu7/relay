# 2026-10-13 — M4: the `relay` command

## What I built
The `relay` command, installed on the PC with `npm link` so it works from any folder in PowerShell or Git Bash:
- **`relay init <project>`** turns any project into a lead + builder pair. It creates the lead's folder next to the project, writes both sessions' instructions and hooks, and adds a `/relay-start` command to the builder. It never changes the project's own `CLAUDE.md`, `settings.json` or `.gitignore`. Running it twice changes nothing.
- **`relay init --undo`** takes all of that out again, restoring changed files byte for byte.
- **`relay start`, `status`, `log`, `pause`, `resume`, `stop`** watch and control a run.

The proof is spike 011. On a fresh git project, `relay init`, then `/relay-start` and one goal, gave **3 automatic rounds** and a working, tested result. The project's own files were unchanged and `git status` stayed clean. The first attempt found a real problem (bug 002), fixed in the lead's template.

## Why it's built this way
**No background Helper** (ADR 0005). The original plan had a Relay Helper process holding the baton. But since M3, the hooks already do everything it was meant to do. So `relay start` just clears the stop and pause flags and resets the round counter. Nothing needs to stay running, which means nothing to restart after a reboot and nothing to crash in the background.

**Don't touch the user's files** (ADR 0006). This drove most of the design:
- The builder's instructions go in **`.claude/rules/relay-builder.md`**. Claude Code loads every file in `.claude/rules/` into each session automatically, so we didn't even need the `@import` line Dennis suggested.
- The builder's hooks go in **`.claude/settings.local.json`**, the settings file meant for personal, uncommitted settings. If one exists, Relay **merges** into it.
- Relay's new files are hidden from git through **`.git/info/exclude`**, git's local-only ignore list. That leaves the committed `.gitignore` alone.

**Undo had to be exact *and* safe.** Restoring a backup is exact, but Claude Code writes to `settings.local.json` when you approve a permission prompt. Blindly restoring a backup would throw those approvals away. So undo looks at each file:
- if it still holds exactly what Relay wrote, the original goes back byte for byte;
- if it has changed since, only Relay's entries are removed.

**Idempotent by design.** Init doesn't "add hooks". It works out what each file *should* contain, given what's in it now, and writes only the files that differ. Running it again gives the same desired content, so nothing is written.

## How `relay init` works, step by step
1. **Find the folders.** `C:\work\my-app` gets the lead folder `C:\work\my-app-lead`. The project name comes from the folder name (`My App` becomes `My-App`) unless `--name` is given.
2. **Work out the config.** If `my-app-lead\relay.config.json` already exists, it's the source of truth, so editing it and re-running init updates the hooks. Otherwise defaults are used: 20 rounds, `rewake`, 3600 s.
3. **Plan every file.** Each plan is a path, a kind (`owned`, `settings` or `block`) and a function: "given the current content, what should it be?" (`init.ts` lines 175–219).
4. **Compute everything before writing anything.** If a settings file is broken JSON, init stops with nothing changed (`managed.ts`, lines 90–94).
5. **Save the install manifest first** (`~/.relay/my-app/install.json`). For each file it records whether it existed, its original content, and what Relay wrote. Saving before writing means even a half-finished init can be undone (line 115).
6. **Write only the files that differ.** Record any folders created, so undo can remove them if they end up empty.
7. **Print the next steps.**

## Code walkthrough

### `packages/helper/src/settings.ts`: merging into someone else's JSON
- Lines 39–56: `relayHookGroups` builds Relay's two hook entries from the config: `asyncRewake: true` only in rewake mode, and `timeout` from `timeoutSeconds`.
- Lines 63–70: `isRelayGroup` recognises Relay's entries **by the script they run** (`…/hooks/dist/bin/stop.js`), with backslashes turned into slashes first. So nothing extra needs to be stored in the user's file to find them again.
- Lines 73–104: `removeRelaySettings` filters those entries out, then tidies up any container left empty. It also removes the block-cap env value, but only if it's Relay's value.
- Lines 111–142: `addRelaySettings` **removes first, then adds**. That's why it's idempotent: running it on its own output gives the same output, and switching delivery modes replaces the entries instead of adding a second set.

### `packages/helper/src/managed.ts`: write, remember, undo
- Lines 26–37: `ManagedFile`, the record kept for each file. `written` is the key field: if the file still equals it, nobody has touched the file since Relay did.
- Lines 83–125: `applyPlans`. It reads and computes everything first, saves the manifest, then writes only what differs.
- Lines 134–166: `undoFile`. Line 151 restores the original exactly when the file is unchanged, or for Relay-owned files. Lines 155–165 handle a changed file: remove only Relay's part, and delete the file only if Relay created it and nothing else is left in it.

### `packages/helper/src/init.ts`
- Lines 66–76: `findGitExclude` walks up to the repository root, because a project can be a subfolder of a repo. It skips worktrees, where `.git` is a file, not a folder.
- Lines 201–219: the exclude lines are written as git patterns, with `/` at the start (anchored to the repo root) and `/` at the end for a folder. That trailing slash was a real test failure: `path.relative` drops it.
- Lines 240–end: `undo` reverses the manifest, removes empty folders Relay made, keeps the lead folder if someone put other files in it, and deletes `~/.relay/<project>/`.

### `packages/helper/src/status.ts`
- Lines 10–18: `batonHolder` turns the state into plain words: who should act next.
- Lines 23–32: `waiterHealth` checks whether the recorded waiter's PID is still running (`process.kill(pid, 0)` sends no signal, it only checks), and whether its deadline has passed. That's how a dead waiter shows up without a background watcher.

## New concepts

### `npm link`
`npm link`, run inside a package folder, makes that package available as a global command. It does this with a **link** (a shortcut) to your folder rather than a copy. Change and rebuild the code, and the `relay` command uses the new version straight away. On Windows, npm creates `relay`, `relay.cmd` and `relay.ps1` launchers in `%APPDATA%\npm`, which is on the PATH.

### Idempotence
An operation is idempotent if doing it twice has the same effect as doing it once. The trick used here: describe the **desired end state** ("this file should contain X") instead of an action ("append X"). Example: `addRelaySettings(addRelaySettings(s))` equals `addRelaySettings(s)`.

### A manifest for undo
To undo safely, record what you're about to change **before** you change it: which files, what they held, what you wrote. The record lives outside the project (`~/.relay/<project>/install.json`), so undo can't be confused by the project's own files.

### Local-only git ignore
Besides `.gitignore`, which is committed and shared, git reads `.git/info/exclude`. It has the same syntax, but it lives inside the `.git` folder and is never committed. It's the polite way for a tool to hide its own files.

### Testing a CLI without a terminal
Every command takes a `CliContext`: the current folder, Relay's home folder, the clock, "is this PID alive?", and a `print` function. Tests pass a temporary folder and collect the printed lines in an array. Only two tests start the real built `relay.js`, to prove the packaging and the real paths work.

## Self-check
1. Why does Relay put the builder's instructions in `.claude/rules/` instead of adding to `CLAUDE.md`?
2. Undo has two ways to put a settings file back. When does it use each, and why not always restore the backup?
3. What makes `relay init` idempotent?
4. Why is the manifest saved before any project file is written?
5. In the first real run, the lead wrote "Looks good." before `TO CODE:`. Why did that end the run, and why was the template changed rather than the parser?

<details><summary>Answers</summary>

1. Claude Code loads every `.claude/rules/*.md` file automatically, so Relay can add instructions without editing any file the user owns. Editing `CLAUDE.md`, even with marker lines, would change their file and show up in `git diff`.
2. If the file still holds exactly what Relay wrote, undo restores the original byte for byte. If it changed since, for example because Claude Code saved a permission approval, undo removes only Relay's entries. Always restoring the backup would silently throw away those later changes.
3. Init computes each file's desired content from its current content, and `addRelaySettings` removes old Relay entries before adding. The same input always gives the same output, and files that already match aren't written.
4. So undo always knows the originals, even if init stops half-way (a crash, a full disk, a locked file).
5. The parser only reads a tag at the very start (the M2 rule), so the reply counted as untagged and went to Dennis. Changing the parser would change a protocol Dennis had accepted, and risks acting on a `TO CODE:` that's only quoted. The template now states the rule with an example, and that worked in the rerun. Whether to relax the parser is a question for Dennis (backlog).

</details>
