## Why it's built this way
- **`engines: ">=22.12.0"`, not `">=22"`.** Vitest 5 declares `node: '^22.12.0 || ^24.0.0 || >=26.0.0'`. With a bare `>=22`, someone on Node 22.4 would pass npm's engines check and then hit a confusing failure when running the tests. Stating the real minimum is more honest.
- **ADR 0001 got a dated "Update" paragraph instead of a rewrite.** An ADR records what was decided *at the time* and why. Rewriting it would hide the fact that we started on Node 20 and why that changed. Superseding the whole ADR would be overkill for a version bump.
- **Defining a "round" in the brief** (`docs/PROJECT_BRIEF.md`, Rounds section). A safety limit ("max 20 rounds") is useless if nobody agrees what it counts. Pinning the definition down now means M2 (state files) and M3 (hooks) can implement and test it exactly.

## New concepts
### Status badge
A small image in the README that shows live status, here "CI passing" or "CI failing". GitHub generates it for each workflow. For a portfolio repo it's a quick trust signal: the code builds and the tests pass on a clean machine.
```md
[![CI](https://github.com/<user>/<repo>/actions/workflows/ci.yml/badge.svg)](https://github.com/<user>/<repo>/actions/workflows/ci.yml)
```

### `gh` (GitHub CLI)
GitHub's command-line tool. It lets you do GitHub work from the terminal: view a repo, list and watch CI runs, call the API. Examples used today:
```
gh repo view dennismugu7/relay --json isEmpty     # check the repo exists and is empty
gh api users/dennismugu7 --jq .name               # read the profile's display name
gh run watch <id> --exit-status                   # follow a CI run live; non-zero exit if it fails
```
