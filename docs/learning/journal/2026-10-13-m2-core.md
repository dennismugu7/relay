# 2026-10-13 — M2: the core library

## What I built
`packages/core`: the shared library the hooks (M3) and the `relay` CLI (M4) will use. It does four jobs:
- **reads a reply's tag** (`TO CODE:` / `TO DENNIS:` / none) to decide where the reply goes;
- **loads and checks** a project's `relay.config.json`;
- **keeps the shared state** in `%USERPROFILE%\.relay\<project>\state.json`: the message queue, each session's waiter, busy flag and re-arm marker, the round counter, and the paused/stopped flags;
- **writes the activity log**, `activity.jsonl`.

It's pure library code: no hooks, no CLI, no Claude Code sessions. 115 tests cover it, including two separate processes changing the state at the same moment.

Before the code, I finished the M1 paperwork. ADR 0002 is now accepted, with Dennis's amendment: a reply to the hook's own re-arm (`WAITING`) must never end the run. The hook recognises it by a **re-arm marker** in the state file, and that marker is part of the state built here. The stage plan was updated to match, and spike 007's phone display was recorded as not observed.

## Why it's built this way
**The hard part is the state, not the parser.** In Relay, three kinds of process touch the same file: the lead's hooks, the builder's hooks and the CLI. They are separate programs that can run at the same moment. Two things can go wrong:
1. **A torn file.** A process is halfway through writing `state.json` when another reads it, or when it crashes. The JSON is broken.
2. **A lost update.** Process A reads the state. Process B reads the same state. A adds a message and saves. B increments the round counter and saves, writing over A's version, so A's message is gone.

The fixes: write atomically (temp file, then rename) for problem 1, and take a lock around every read-change-write for problem 2. ADR 0003 compares this with SQLite, a lock library, and "only the helper writes". I chose the plain file version because it has no dependencies, Dennis can open `state.json` and read it, and each piece is small enough to understand.

**The lock is proven, not assumed.** The two-process test passes with the lock. I then removed the lock on purpose and ran it again: `expected 64 to be 100`. More than a third of the updates were lost. With the lock back, it passed again. A concurrency test that has never failed proves nothing, so seeing it fail first is the important part.

**Plain helpers, not a class.** The state is a plain object. Callers change it inside `updateState`, for example `updateState(dir, (s) => { s.paused = true; })`. Helpers exist only where there's a rule to get right: the queue, the one-waiter rule and the round limit.

**Alternatives for the tag parser:** splitting the first line and comparing strings would need many special cases for markdown. A single regular expression, commented piece by piece, is shorter and easier to test with a table of examples.

## Code walkthrough

### `packages/core/src/tags.ts`
- Lines 24–33: `TAG_PATTERN`. The comment above it reads the pattern left to right: leading whitespace, an optional `#` heading or `>` quote, optional `**`/`__`/`` ` `` markers, the words `to` and `code`/`dennis` with any spacing, then the colon, with markers allowed on either side. The `i` flag makes it case-insensitive.
- Lines 41–53: `parseTag`. No match means "to Dennis" with the whole reply as the body. A `TO CODE:` with an empty body also goes to Dennis, because there's nothing to deliver. The `^` at the start of the pattern is why a tag later in the reply doesn't count.

### `packages/core/src/config.ts`
- Line 42: `isValidProjectName`. The project name becomes a folder name under `~/.relay/`, so it may only contain letters, digits, `.`, `_` and `-`, with no `..`. Without this check, a name like `../../Windows` could point outside Relay's folder (a **path traversal**).
- Lines 55–98: `parseConfig` collects *every* problem before throwing, so one error message lists them all. It fills in defaults for `maxRounds` (20) and `delivery` (`"rewake"`).

### `packages/core/src/lock.ts`
- Line 63: `open(lockPath, 'wx')`. The `x` means "fail if the file exists". The operating system guarantees that only one process can create the file, which makes it a lock.
- Lines 57–84: the retry loop. If someone else holds the lock (`EEXIST`, or `EPERM` on Windows while a file is being deleted), wait a little and try again. The wait has a random part so two waiting processes don't keep colliding in step. After `timeoutMs` the loop gives up with an error naming the holder.
- Line 87: `removeIfStale`. If a process crashed while holding the lock, the lock file stays forever. A lock older than 10 s is treated as abandoned, since normal updates take milliseconds.
- Line 98: `release` deletes the lock only if it still holds *our* token. If our lock had been broken as stale and someone else took it, we mustn't delete theirs.

### `packages/core/src/atomic.ts`
- Lines 41–50: `writeFileAtomic` writes `state.json.<pid>.<random>.tmp`, then renames it over `state.json`. A rename in the same folder swaps the file in one step, so readers see the old file or the new one, never half of each.
- Lines 22–38: `renameWithRetry`. On Windows, a rename can fail for a moment (`EPERM`, `EBUSY`) while another program, such as an antivirus scanner, has the file open. The function retries a few times. The real `rename` can be swapped for a fake in tests, which is how the retry is tested without needing a real antivirus.

### `packages/core/src/state.ts`
- Lines 19–69: the types. They're the real "spec" of the state file. Each field has a comment saying who sets it and why.
- Lines 93–112: `readState` returns the initial state if there's no file yet, and throws a `StateError` naming the file if it's broken.
- Lines 137–153: `updateState`: lock → read the latest state → `change(state)` → atomic write → unlock. `change` is synchronous on purpose, so nobody can hold the lock while waiting on something slow. If `change` throws, nothing is written.
- Lines 185–202: the one-waiter rule from ADR 0002. `registerWaiter` replaces any older waiter. An old waiter checks `isCurrentWaiter` before delivering. `clearWaiter` only removes a record that belongs to the caller's PID.
- Line 208: `startRound` refuses once `maxRounds` is reached. Resetting is just `s.rounds = 0` when control returns to Dennis.

### `packages/core/src/activity.ts`
- Lines 41–55: `appendActivity` adds one JSON line under its own lock (`activity.lock`), so lines from two processes never mix. `JSON.stringify` turns line breaks inside a message into `\n`, so each entry stays on one line.
- Lines 61–79: `readActivity` skips a damaged line (say, half a line left by a crash) instead of failing the whole log.

### `packages/core/src/__fixtures__/`
`concurrent-worker.ts` is a tiny program that does N updates in a loop. `run-workers.ts` starts two copies with `node --import tsx` at the same moment. **tsx** lets Node run the TypeScript source directly, so the test doesn't need a build first. The folder is left out of the build (`tsconfig.build.json`).

## New concepts

### Race condition and lost update
A **race condition** is a bug that depends on timing: two things happen "at the same time" and the result depends on which goes first. A **lost update** is the classic case. Two processes both read `rounds: 5`, both write `rounds: 6`, and one increment disappears. Example: without the lock, 2 × 50 increments gave 64 instead of 100.

### Lock file
A file whose existence means "someone is busy with this". Create it with `fs.open(path, 'wx')`, which fails if it already exists, do your work, then delete it. Only one process can create it, so only one works at a time. You need a plan for **stale** locks left by a crashed process (here: older than 10 s means abandoned).

### Atomic write (temp file + rename)
"Atomic" means "all or nothing". Write the new content to `state.json.123.tmp`, then `rename` it to `state.json`. The rename replaces the file in one step, so nobody ever sees a half-written file. Example: `await writeFile(tmp, data); await rename(tmp, file);`.

### JSON Lines (`.jsonl`)
A text file with one complete JSON object per line. Adding an entry means appending one line, with no need to rewrite the file. A damaged line only loses that one entry. Example line: `{"time":"2026-10-13T10:00:00.000Z","project":"app1","kind":"paused"}`.

### Type guard
A function that returns `value is SomeType`. When it returns true, TypeScript treats the value as that type from then on. `looksLikeState(value): value is RelayState` lets `readState` return parsed JSON as a `RelayState` safely.

### Path traversal
Using `..` or slashes in user-supplied text to reach files outside the intended folder. `path.join(home, '../../secret')` leaves `home`. The fix is to allow only safe characters, which is what `isValidProjectName` does.

## Self-check
1. Atomic writes alone don't stop lost updates. Why not?
2. Why does `release` check the token in the lock file before deleting it?
3. Why is `updateState`'s `change` function synchronous?
4. Why does `parseTag('TO CODE:')` go to Dennis?
5. Why must the project name be validated before it's used in a path?

<details><summary>Answers</summary>

1. An atomic write makes sure each write is whole, but two processes can still both read the same old state, change it, and write. The second whole write replaces the first whole write. Only a lock around read-change-write prevents that.
2. If our lock was judged stale and another process took over, the file now belongs to them. Deleting it would let a third process in while they're still working.
3. So no caller can hold the lock while waiting for something slow (a network call, a timer). The other processes would be blocked the whole time, and could eventually time out.
4. A tag with an empty body has nothing to deliver to the builder, so the safe default applies: hand control to Dennis.
5. The name becomes a folder under `~/.relay/`. A name with `..` or slashes could make Relay read or write files elsewhere on the disk (path traversal).

</details>
